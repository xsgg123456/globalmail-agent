## 有序交付与完成标准

1. **事项与方案**：沿用 CaseIssue，按核验订单行与有源诉求持久关联；会话保留多个事项、方案及当前等待。客户改选必须先查询/取消旧申请，未知或已发货不能假装取消，也不能重复赔付。完成标准：同客户两订单各有待办；改方案的成功取消、不能取消、未知三种真实事务路径有证据。
2. **事件与等待**：0009增量迁移已有事项/等待/wake和消费关联；复用当前锁、任务与 AgentRunner。业务结果必须关联实际申请或相关事项，覆盖早到、晚到、重复、乱序、无关；排队不标消费，完成运行只消费其实际观察的事件。完成标准：FT-02/03/06/07时序反例通过；HITL、人工回复后等待客户、停止/中断和已结案时只记账、不自动出站。
3. **连续业务事实**：复用同一业务账本与模拟控制台，扩展订单/事项关联的库存、地址、原包裹、退件资料和质检修订；修订带来源、版本和原因，历史保留。完成标准：库存/地址无凭证仍拒绝，旧版本/异分支/重复输入拒绝或幂等；退货后退款、补件后查物流、取消及纠错均不绕过授权和执行前置条件。
4. **连续流程驱动与报告**：驱动单独读 controller-events，只把已达 gate 的当前客户/人工/业务事件交给实际服务，不将参考回复或未来控制资料注入 Agent。完成标准：21 JRN及原51输入逐项有结果；gate具名证据、实际运行/账本编号、阻塞原因及未运行状态完整；参考答案读取与运行加载器隔离。
5. **工作台**：沿用已有组件、布局和设计规范展示多事项、关联订单行、当前方案、等待和业务事件版本/消费状态。完成标准：真实API数据、加载/错误/空态、宽窄及明暗页面验证；人工执行业务与接管按钮独立。
6. **冻结验收与交接**：真实隔离PG/HTTP/Graph故障测试、前端测试、编译、浏览器、fresh两阶段审查；修复后重新冻结相关证据，清理测试数据，只读核验正式库和160原件；主Agent本地中文Git提交。完成标准：工程四步均有当前源码证据；不勾82项全项目AC、不改写Phase1/7/8质量FAIL。

## 数据与质量边界

原21 JRN含81个人类文字checkpoint及部分缺库存规格/快照、地址来源字段的输入，不能自动当作已通过或暗填成授权。原资料保留；驱动将缺失前提列为blocked/awaiting_checkpoint，并允许显式、有来源的模拟准备资料或人工检查证据。固定响应工程测试只证明真实服务、状态与gate执行，不冒称实际模型完成全部21条业务质量旅程。付费模型语义及最终人工验收继续在Phase13统一回归。

资料/API与状态契约有变更时先更新主架构，再改实现。新代码文件≤300行，测试使用随机私有schema与独立对象目录；原件和正式设置只读。.idea不编辑、不提交。
