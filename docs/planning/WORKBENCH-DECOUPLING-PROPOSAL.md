## 2. 排查结论

### 2.1 用户看到的拥挤有明确的聚合点

`frontend/src/components/mail-agent/AgentProcessPanel.vue:71–90`同时挂载事项、案件记忆、业务数据、售后申请/模拟执行和人工处理；其上方又展示Agent运行。`views/mail-agent/index.vue`将这些内容固定放在360px右栏，窄屏改为同一组内容的抽屉。页面使用同一个客户上下文承载多种任务，这是职责和信息层级上的耦合。

并非全部状态都塞在一个全局loading里：运行明细、业务查询和售后操作已有独立composable。需要保留已有的幂等、版本及过期请求防护，再拆路由、资源订阅和上层组织。

### 2.2 模拟资料经过后端服务持久化，问题是入口混在业务页面

独立审查已追到生产组件→API→受控初始资料包→独立PG模拟分支；没有发现邮件生产组件把示例客户和订单写死成正常响应。当前工作台把“创建初始业务场景”、业务读模型和人工模拟执行入口混放，因此演练设置与正常邮件处理互相干扰。应移动入口并保留真实来源标记，不删除为后端工程验证准备的资料。

### 2.3 刷新范围跟着会话整体走

`useMailWorkbench.ts:64–104`读取整个ConversationDetail；邮件页面的SSE回调同时刷新会话和列表。`useAgentRunDetails.ts`监听整个detail快照，快照更新会重读展开的运行。已有请求generation和单次刷新合并保护；本轮没有测量请求耗时或复现串客户，不把结构问题写成已证性能故障。

独审还发现抽屉`destroy-on-close`和宽窄切换会卸载处理面板；`useAfterSales`的未知命令/原key及模拟表单存于该组件实例。界面关闭后存在失去原请求核对依据的恢复风险，但本轮未执行模拟命令，没有重复交易实测。拆分时应让未确认命令按分支/操作保存在独立模块生命周期中，并补关闭重开/切换页面的真实丢响应验收。

### 2.4 完整Agent观测还缺逐次模型调用记录

| 内容 | 当前代码证据 | 现状 |
|---|---|---|
| 结构化邮件理解 | `application/run_records.py:51–66` | 已保存并可读取 |
| 工具名称、参数、结果和状态 | `application/run_records.py:67–73` | 已保存并可读取 |
| 回复产物、引用、等待与累计用量 | `application/run_records.py:74–83` | 已保存并可读取 |
| 模型思考开关 | `adapters/model_provider.py:36–41` | 理解/决策关闭；OutcomeReview开启，thinking_budget=2048 |
| 供应商返回的思考 | `adapters/model_provider.py:55`、`agent/graph.py:45–71` | 适配器接收reasoning_content；图只处理用量和正文/工具，没有逐次持久化或展示通路 |
| 每次实际请求的完整文字提示词及参数快照 | `agent/graph.py:82–90`及validation请求组装；`agent/context.py:122–126` | 有运行上下文和版本字段，但没有每次请求的不可变快照API |
| 网络重试和每次请求的用量 | `agent/budget.py:46–89` | 有request_key、stage、预留及结算；当前运行API主要返回累计用量 |
| Trace关联 | `worker/agent_runner.py:43–49` | 已登记local_only trace_id；正式Langfuse服务尚未接入 |

Graph checkpoint保留部分状态，但不能拿它替代逐次请求快照：工具菜单会变，核验使用独立提示词，失败返回不一定进入成功节点状态。读取当前磁盘上的prompt也不能还原以前实际发送的文字。

### 2.5 当前设计与新要求的关系

原Spec的REQ009和CMP004规定右侧处理/人审区，REQ008（第403行）只要求简短说明和可验证工具记录，并未要求存储或展示隐藏思维链。独立运行台、每次完整文字请求及供应商返回思考属于本轮新增观测/交互要求；不能把这些新要求的缺失倒写为原阶段已验功能的失败。REQ013及Phase11原有追踪、脱敏和观测降级仍需一并对齐。

## 3. 页面职责与跳转

| 页面 | 职责及默认内容 | 推荐入口 |
|---|---|---|
| 邮件工作台 | 客户/会话列表、正常邮件往来、图片、人工回复/接管/结案；轻量Agent状态与“查看本轮运行” | `/workbench?conversation_id=…` |
| Agent运行台 | 每轮实际执行时间线、模型调用、提示词与输入、返回思考/正文、工具请求与结果、核验、重试、等待、错误与提交结果 | `/agent-runs/:run_id`，支持按会话查看历史运行 |
| 业务数据中心 | 订单及商品行、库存、物流、售后申请、执行回执；显示当前状态、来源、历史版本及关联运行 | `/business`，以订单/操作及受控分支上下文定位 |
| 场景实验室 | 选择/创建模拟场景、追加模拟客户输入、推进库存/物流/退款/收货/质检、模拟取消/纠错回执 | `/simulation`，只允许对应交互模拟分支写入 |
| 知识库 | 保留现有资料维护、构建、发布、检索试查流程 | `/knowledge` |

新增URL只是拟议路由，不是当前已实现入口。

邮件中只显示“Agent处理中/等待客户/等待业务/待人工/失败”等状态及运行入口，不把调试提示词写进邮件正文。Agent运行台必须常驻侧栏导航，用户可以从邮件定位某轮，也可以直接筛选全部运行。业务中心的人工模拟执行使用“进入场景实验室”链接，不在普通读模型旁混入模拟按钮。

邮件、运行、业务页靠conversation_id、run_id、operation_id和服务端校验的scope关联；不能各自复制一份订单或把URL参数当授权。返回邮件时恢复会话、阅读位置和未提交草稿；从工具结果查看业务状态后可回到原运行和节点。历史模式的对照回复继续独立保存，不能混入真实历史邮件。

## 4. Agent运行台交互

### 4.1 页面组织

左侧为运行列表/筛选，主体为真实事件时间线，详情区查看选中节点。顶部保留客户会话、触发邮件、模式、分支、run状态、时间、累计用量、返回邮件和查看关联业务入口。停止/显式重试沿用原服务控制条件。

每一次模型调用、工具执行及程序校验各占一个节点。按真实发生顺序展示，不预填“已理解→已查单→已退款”固定成功步骤；同一循环反复调用工具和模型时保留所有次数。人工控制台操作标为“人工模拟操作”，程序拒绝标为“程序校验”，避免混称AI执行。

节点详情建议采用“概览 / 实际输入 / 供应商思考 / 实际输出 / 工具及结果”分区。请求输入包含实际system/user/tool消息、当次工具Schema、response_format、模型参数、思考开关、prompt内容/hash及版本、输入来源。思考区只展示供应商实际返回的reasoning_content，明确区分未启用、未返回、被预算截断、请求失败和历史未记录；不能根据理解结果生成一段解释冒充原思考。

### 4.2 思考与流式展示的实施边界

Qwen3.7-Plus支持按请求启停思考；官方兼容接口区分reasoning_content和content，支持相应模型的同步或流式输出，见[百炼深度思考文档](https://help.aliyun.com/zh/model-studio/deep-thinking)。因此可展示的是接口实际返回的思考文本，不承诺获得模型未返回的所有内部过程。

建议先补忠实的逐次采集和节点级实时状态，保留当前思考开关与6模型/12工具/120活动秒预算；如需要逐字思考/输出，再实现provider流式组装与断流处理。若要求理解和决策也产生思考，须另行对齐产品预算和结构化输出/工具调用实测，不能把页面重构默认为已授权全节点调参。

## 5. 技术拆分边界

### 5.1 前端按资源持有状态

- 邮件模块管理列表、邮件读取、输入草稿与人工通信；Agent模块以run_id管理运行/节点；业务模块以受控branch/order/operation管理读模型；实验室持有场景创建与模拟事件命令。
- 复用现有API客户端、类型、组件、PendingCommands和版本保护。`AgentToolRecords`、引用抽屉、订单卡、账本等可迁移/复用；`AgentProcessPanel`的多职责聚合需要拆开。
- 跨页仅共享导航定位及必要的资源缓存，不共享一个全局busy/error来锁所有页面。事件通知按资源ID失效/增量追加；未打开的重型业务面板不跟每个Agent事件重新读取。
- 深链接恢复当前会话、运行和节点；打开/刷新观察页面只读，不触发模型、重跑业务或创建场景。

### 5.2 后端增加观测投影，复用原业务契约

保持现有模块化单体、业务状态机、权限与去重契约。前端职责拆开不要求拆微服务或复制账本。

新增逐次模型调用/步骤投影：以run、request_key、attempt和sequence记录节点身份、父子关系、阶段、开始结束、状态、prompt/request正文对象引用、供应商响应正文/思考对象引用、provider_request_id、当次usage、tool_call_id和业务command/operation关联。逐次参数在ModelProvider实际options构造后采集，保留动态工具菜单和修复请求；图像以受控附件ID、摘要与视图引用表示，不复制base64。

拟增`GET /runs/{id}/steps`与单节点详情、可续读的步骤事件；沿用已实现的stop/retry。邮件读取与运行摘要、完整运行内容按需分开，业务和模拟使用已有独立API。最终表/API命名须在实施前同步主架构，不在方案里冒充已存在契约。

本地受控正文查看与Langfuse脱敏导出分开：本机运行台可以按原scope读取获准文本快照；不向前端提供API凭据/请求认证头，不把原始图片、真实身份自由文本默认导出。正文对象登记来源/依赖并遵循撤销、删除、过期运行的读取门；追踪记录不可绕过图片撤销。观测中断标为不完整，不为了补记录重跑模型或业务。

后续Phase11可将同一调用/步骤映射到自托管Langfuse，不新建第二套Agent执行器；业务提交仍以业务数据库为准。Langfuse官方建议逐次generation与tool构成关联树，而非将整个循环聚合成一次调用，见[追踪最佳实践](https://langfuse.com/docs/observability/best-practices)。

## 6. 实施顺序与验收

| 顺序 | 交付 | 完成标准 |
|---|---|---|
| 1 | 更新源需求/主架构/开发计划的UI职责及本地观测契约 | 调整REQ009、第7节CMP004及业务/模拟入口的聚合设计；新增运行/业务/实验室页面与验收映射，说明思考开关边界 |
| 2 | 补逐次请求/响应和步骤记录 | 在隔离服务对照真实发出请求，提示词、动态工具Schema、输出/思考、每次重试均可对应；未思考/断流/超时/晚到/撤销如实展示，usage不重复 |
| 3 | 建独立Agent运行台与跨页定位 | 从邮件一键到正确run；刷新不执行模型；按真实顺序查看工具及所有请求，返回保留邮件草稿/阅读位置；记录失败不让邮件交互不可用 |
| 4 | 将业务读模型和模拟控制移出邮件工作台 | 邮件正常查看不读取模拟控制内容；业务中心与实验室独立加载/错误/幂等；多客户/多分支切换不串记录，历史模式不能写模拟账本 |
| 5 | 工程回归、实际交互与范围审查 | 验证明暗主题/窄屏/断网恢复、事件重连、停止重试、相同原请求核对、未发布知识、越权与撤销；保留原模型质量失败及总验收待办 |

实施采用现有Art Design Pro布局、组件、主题和图标，不引入新视觉体系。ui-ux-pro-max用于深链接、返回行为和渐进展示检查；其自动设计搜索命中FAQ/夸张极简，和本项目工作台不符，未采纳该风格、字体或配色。

本轮仅给方案：原Spec、主架构和DEV-PLAN暂保留现有实施基线。用户要求实施时，先同步这些源文档及CHANGELOG，再按上述可独立验收的步骤开发。
