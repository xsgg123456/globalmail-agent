# 知识管线专项实测

日期：2026-10-07；实验输入：Product-Spec v1.10、KNOWLEDGE-DESIGN v1.0。代码及结构化证据位于 [knowledge-spike](../../globalmail-agent/knowledge-spike/README.md)。本轮是可复跑的组件与最小契约实验，正式知识管理应用尚未实现。

## 本轮结论

1. 简单文字资料保持直接解析；复杂或扫描 PDF 推荐 MinerU Basic。Standard 在本组困难样本上没有增加关键内容覆盖，但耗时更高，保留为升级路径。
2. 新的 qwen3.7-text-embedding 1024 维推荐作为下一阶段主候选，text-embedding-v4 保留对照/回退配置；两者均已实接同一百炼北京端点。新模型在冻结开发问题上的首位排序更好，不能据此宣称生产准确率。
3. 当前 SOP/案例很短，保留完整语义优于无条件切碎。长文再按章节/步骤切子块，召回后按父文档去重、补齐前提和警告，并受上下文预算限制。
4. 新索引就绪后切换发布清单、独立模型空间、下架代次检查与删除栅栏在隔离 PostgreSQL 中可行。正式对象清理、持久化 worker、政策同版发布及 UI 仍需实现。

## 解析输入及结果

真实来源整理的现有产品 PDF 为 17 页、8 张商品图，覆盖 34 个 SKU。额外构造两份 4 页开发样本：多栏、16 行跨页参数表、中文警告、图片中的操作步骤；一份保留文字层但第 4 页为图片，另一份全部扫描化。虚构型号与参数只用于解析测试，不进入知识或客户回答。

| 解析器 | 原说明书 17 页/34 SKU/8 图片 | 混合样本关键项 | 扫描样本关键项 | 参数表完整行 | 混合/扫描耗时 |
|---|---|---:|---:|---:|---:|
| pypdf | 通过存在性检查 | 17/21 | 0/21 | 0/16、0/16 | 0.45 / 0.44 秒 |
| MinerU Flash 文字模式 | 通过存在性检查 | 17/21 | 0/21 | 14/16、0/16 | 4.06 / 4.30 秒 |
| MinerU Basic | 通过存在性检查 | 21/21 | 21/21 | 16/16、16/16 | 8.58 / 11.27 秒 |
| MinerU Standard | 本轮未重复原说明书 | 21/21 | 21/21 | 16/16、16/16 | 14.00 / 34.11 秒 |

Basic 对现有说明书耗时 19.91 秒，进程树 RSS 峰值约 2206 MiB；Standard 在两个困难样本的峰值约 2071/2151 MiB。这里测的是包含进程启动的单次墙钟时间与进程内存，不是 GPU 峰值、稳定吞吐或负载测试；缓存和模型初始化会影响结果。本机显卡为 RTX 5060 Ti 8 GB，Standard 使用本地 llama.cpp 路径完成。

样本渲染已查看，无文字裁切和表格行重叠；Basic 的多栏输出先完整保留 ALPHA 步骤及停止条件，再进入 BETA。Flash 保留了文字但标题/两栏正文的顺序不适合直接按线性标题归属，且表格漏掉两行结构信息。后续同页多型号仍须依据块位置/章节绑定适用范围，不能仅凭解析顺序自动赋予 SKU。

MinerU 导出的 Markdown 可能内嵌图片数据；实验使用结构化块并排除图像编码，避免把 base64 送去 Embedding。图像对象存在不等于其维修含义已验证；本组仅验证关键文字、表格单元及图像/位置存在性。

证据：[解析对照](../../globalmail-agent/knowledge-spike/parsing-results.json)、[Standard 对照](../../globalmail-agent/knowledge-spike/parsing-standard-results.json)。版本为 MinerU 4.0.10、DocVortex 0.5.9；独立环境 115 个包锁在 [依赖清单](../../globalmail-agent/knowledge-spike/mineru-requirements.lock)，约 2.10 GB 模型文件摘要在 [model-assets.json](../../globalmail-agent/knowledge-spike/model-assets.json)。MinerU 所需 OpenAI SDK 2.x 与原技术探针 3.x 分环境，不直接合并依赖。

## Embedding 与切分对照

查询在模型调用前编制并冻结：36 条正例、12 条边界、6 条无答案、6 条多证据，英德各 30 条。标签指定逻辑文档与原文关键短语，不能命中同篇任意块就算正确；查询和答案均不进入知识索引。来源与限制见 [查询说明](../../globalmail-agent/knowledge-spike/query-set-notes.md)。

| 模型与切法 | 正例首位含关键证据 | 正例前五含关键证据 | 多证据前五全部覆盖 |
|---|---:|---:|---:|
| v4，整篇 | 18/36 | 36/36 | 6/6 |
| 新模型，整篇 | 29/36 | 36/36 | 6/6 |
| v4，固定 500 字符窗口 | 10/36 | 31/36 | 2/6 |
| 新模型，固定 500 字符窗口 | 19/36 | 35/36 | 4/6 |
| v4，结构切分、未按文档去重 | 17/36 | 30/36 | 2/6 |
| 新模型，结构切分、未按文档去重 | 20/36 | 33/36 | 3/6 |

两档结构切分目标为 300/500 代理 tokens，但本批章节都较短，实际都生成 124 块、最大 428 tokens（短案例完整保留）；两档有效输入相同，因此不能从本实验断言 300 或 500 更优。计数使用 Qwen3-Embedding-0.6B tokenizer 作代理，托管模型 tokenizer 完全一致性尚未证实。

问题来自同一 SOP 的多个子块占满 top5。对适用候选取 top20 后按父文档去重，最多取 5 个父文档；仅对不超过 1200 代理 tokens 的短父文档完整展开，总预算 4500。两模型均达到正例 36/36、多证据 6/6，12 条边界始终为空；实际最大上下文为 2525 代理 tokens。长文仍需按适用章节展开，本轮不证明长文最佳参数。

当前每个 SKU 的候选文档很少，top5 经常覆盖大部分适用文档，不能称为“100% 检索准确率”。本轮更有区分力的证据是首位排序、切块后的关键片段覆盖和多资料挤占问题。

首次真实调用中，两模型各调用 26 批、256 个去重输入。v4 报告 42676 tokens、批次耗时合计 63.80 秒；新模型 44317 tokens、44.17 秒。这是一次串行对照，受到网络和服务负载影响，不作为速度 SLA；价格未在本轮重新核算。首次调用证据保存在 [原始检索结果](../../globalmail-agent/knowledge-spike/retrieval-initial-results.json)；审查修复后使用同一输入的向量缓存重算，当前 [检索结果](../../globalmail-agent/knowledge-spike/retrieval-results.json) 按本次实际新增调用计数，另见 [组装结果](../../globalmail-agent/knowledge-spike/evidence-results.json)。

## 资料不足与证据核对

固定选择 6 条正例、6 条多证据、6 条无答案问题，用实际 qwen3.7-plus 检查证据是否足够，并逐字核验其引用来源。初版只通过 13/18：缺少可信运行模式时，模型拒绝使用模拟政策；同时混淆了“可以解释没有完成证据”与“无法回答”，还有原文引用拼接错误。

补齐应用提供的 mode/SKU/as_of，并明确模拟政策仅在隔离演练内有效、无完成证据可以有依据地解释后，同一冻结子集 18/18 通过，其中无答案 6/6 均判为证据不足。初版结果保留在 [evidence-initial-results.json](../../globalmail-agent/knowledge-spike/evidence-initial-results.json)，修订结果为 [evidence-results.json](../../globalmail-agent/knowledge-spike/evidence-results.json)。

这是开发过程的修正与复跑，不能叫独立评测；只验证“证据是否足够”和引用原文，不等于已生成合格客户回复或完成售后决策。正式输出仍需确定性引用校验和人审降级，不能只信任模型返回的 supported 标记。

## 生命周期契约与边界

在随机端口、仅本机绑定的临时 PostgreSQL 18.6 / pgvector 0.8.6 中，使用本轮两套真实 1024 维向量执行七组检查：

1. 首次发布、相同构建幂等与不同输入冲突拒绝。
2. SQL 在向量排序前按已登记 SKU—品牌关系、模式、用途、时间过滤；60 条查询均执行。
3. 未就绪新构建发布失败，旧发布继续可用。
4. 新版本发布与回滚；两条连接分别观察旧事务快照和新发布，单次检索不混版本。
5. 两套真实同维模型切换、失败保旧配置、旧空间查询不能混入新发布。
6. 下架后新查询为空，缓存/待提交引用失效，旧代次任务及发布被拒。
7. 清理实验库内正文与向量后，删除记录阻止重新构建/发布。

首轮发现共享政策的 `SKU ANY` 与 `brand ANY` 分开判断可能串配，修正为 JOIN 已登记 SKU—品牌关系后复验。另有 8 项失败与并发回归，涵盖部分写入事务回滚、未核对发布、过期引用、晚到任务与下架的锁竞争、非法向量与清理故障。

内容版本切换使用合成版本标签及不变真实向量，模型切换使用真实双模型向量；并发失败用显式三维合成向量。实验只清理数据库内容与向量，不代表已实现文件对象/隐私衍生副本清理、备份恢复、政策规则与说明捆绑发布或实际邮件发送。MVCC 旧事务仍可能读到旧数据，提交回复前必须通过新事务核验当前资格。证据：[lifecycle-results.json](../../globalmail-agent/knowledge-spike/lifecycle-results.json)。

## 验证状态与下一步

首次独立审查确认当前实验数值可复现，同时指出父正文复核、失败运行误用旧缓存及并发测试表述三项问题。已补充父子版本/内容/适用范围复核，以及成功运行 ID、源/查询/块摘要和产物摘要关联；下游证据与生命周期实验遇到上游失败或产物陈旧会停止。原始审查保留在 [review-notes.md](../../globalmail-agent/knowledge-spike/review-notes.md)。修复后 fresh 独立复核通过，三项问题均关闭，无新增 HIGH/MEDIUM；包含失败 CLI、旧缓存拒绝、父文档变更、双模型排序及逐条引用复核，证据见 [review-final.md](../../globalmail-agent/knowledge-spike/review-final.md)。该结论只关闭本轮实验，不代表正式应用验收。

修复后 14 个 Python 文件编译通过，115 个依赖包兼容；普通测试实际 24 项，其中 19 通过、5 项数据库测试按设计跳过。另经生命周期入口在真实临时 PostgreSQL 中完成 7 组检查及全部 8 项契约测试，无跳过，数据库和临时凭据均已清理。当前 evidence/lifecycle 输入与成功上游快照的摘要一致，记录见 [verification-results.json](../../globalmail-agent/knowledge-spike/verification-results.json)。

本实验结束时提出的架构细化已纳入 [AGENT-ARCHITECTURE](../../AGENT-ARCHITECTURE.md)，持久化管线、UI、删除范围及新查询验收已安排在 [DEV-PLAN](../../DEV-PLAN.md)；应用实现尚未开始。现有模拟知识继续只允许 simulation，不因技术实验通过就改为生产资料；上述实验结果与原始审查范围不改写。
